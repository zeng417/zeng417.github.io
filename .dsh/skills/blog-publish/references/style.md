# zeng417.github.io 写作风格（从已发布的 7 篇里总结）

## 篇幅与结构

- 200~400 行，中位数约 300 行。少于 150 行显得单薄，超过 450 行要拆。
- 章节用中文序号二级标题：`## 一、先看一个生活场景`、`## 二、Topic：消息的「地址」`。
- 需要细分时用三级标题：`### 1. Retained（保留消息）` 或 `### 订阅时的两个通配符`。
- 常见骨架：痛点引入 → 一句话本质 → 分 6~9 节展开 → 常见误区 → 一句话总结。

## 开头（很固定）

第一段直接说读者为什么会点进来，用第二人称、口语：

> 如果你做过物联网、智能家居，或者只是想让程序在弱网环境下也能稳定收发消息，那你大概率会碰到 MQTT。

接着承认门槛：

> 很多人第一次看 MQTT 文档，会被一堆名词劝退：Broker、Topic、QoS、Retained、Will、Clean Session……

然后给一句本质，用引用块加粗：

> **设备不直接互相说话，而是把消息交给一个「中转站」，谁关心什么消息，就提前跟中转站打个招呼。**

最后一句过渡「这篇文章就用最少的术语，把这个协议讲清楚。」，紧接着一条 `---` 分隔线。

技术教程类还会在开头加一句环境说明：

> 适用环境：ROS 2 Humble（Ubuntu 22.04 / Docker 中的 Humble 均适用）

## 行文习惯

- 第一人称叙述踩坑经历：「我当时」「我一开始以为」。
- 大量生活类比：物业前台订报纸、训狗、走迷宫、挂号信。
- 用「——」破折号补充解释，用「」直角引号包术语（正文里不用 `"`）。
- 关键结论单独成行、加粗，不埋在长段落里。
- 适度用列表，但一段连续 3 行以上的纯文字段更常见——不要写成 PPT。
- 「踩坑」「劝退」「搞定」「翻车」这类口语词可以用，不要写成论文腔。

## 表格

概念对照、参数说明、命令速查一律用表格，表头与分隔行都写 `| --- | --- |`：

```markdown
| 生活里的角色 | MQTT 里的角色 |
| --- | --- |
| 物业前台 / 报社发行部 | **Broker（消息代理）** |
```

## 代码

- 代码块必须标语言：` ```bash `、` ```python `、` ```cpp `、` ```yaml `。
- 命令给可直接复制的最小版本，前面用一句话说明在哪执行。
- 输出结果用注释或单独代码块，不要贴大段无关日志。

## 收尾

最后一节固定是总结，形式二选一：

1. `## 九、一句话总结` + 若干加粗短句的列表 + 一句「学 X 不用背所有命令，但要能回答三个问题……」
2. `## 九、常见问题排查清单` + 编号列表，每条 `**现象**：原因与解法`

有的文章再补一节 `## 附：最小记忆卡片` 做速查。

## 禁止

- 不写「总之，综上所述」「希望对你有帮助」这类套话。
- 不写没有行动信息的句子（「要注意细节」「要小心处理」）。
- 不在正文里塞外链堆，需要引用就一句话说明出处。
- 不用 emoji 当小标题。
