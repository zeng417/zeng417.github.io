如果你在做机器人，早晚会接到这么一句需求：「让它自己走到那个点。」

甲方通常还会补一句「不难吧」。不难，前提是你先问清楚三个问题：哪个点？中间必须经过哪儿？路上有人挡着怎么办？

这三个问题的答案，对应的是三种完全不同的导航方式。麻烦在于，它们在日常沟通里被混着用：招聘 JD 写「熟悉自主导航」，产品文档写「支持点对点导航」，代码注释写「走轨道」，说的可能压根不是一回事。有人调通一次 `NavigateToPose` 就说自己做了自主导航，有人沿磁条跑一圈也叫轨道导航，还有人把底盘的一个 `move_to_location` 接口当成点对点的全部。

> **点对点回答「去哪」，轨道回答「怎么走」，自主回答「路上变了怎么办」。**

这篇文章不讲公式，用我在消防巡检机器人项目里的真实取舍，把这三个词拆开讲清楚：它们各自解决什么问题、代价是什么、什么时候该用哪个，以及为什么最后大多数工业项目其实是三种混着用。

顺带一提，这个项目导航模块的完整实现，我写在[另一篇](/posts/tianyi25-fire-inspection-nav/)里了，这篇只谈选型逻辑。

## 一、先看一个真实的需求

天轶 2.5 消防巡检机器人要干的事很具体：从起点出发，按顺序走到几个巡检点位，在每个点位停下来让视觉模块检查灭火器、消防设施和安全出口，检查完播报结果，最后沿原路返回起点。

我最初的理解是「给几个坐标，机器人挨个走过去」，估了三天工作量。真上手才发现，同一套系统里其实同时跑着三种导航：

- 从起点到第一个点位、以及点位之间，用的是**轨道**——路线预先配好，机器人沿线走；
- 点位本身是**点对点**的目标——给一个 POI 名字，去那个位姿；
- 走的过程中如果前面有人或杂物，需要**局部避障**——这是自主导航里的一小块能力。

三套东西各管一段，谁也不能单独把活干完。这个认识是做到一半才建立起来的，但它决定了后面所有的接口设计：**如果一开始就把它们当成三选一，接口一定会写死在某一种上，后面想混着用就得推倒重来。**

## 二、三个问题，把三种导航分开

判断一段导航属于哪一类，别听名字，问三个问题就够了。

| 问题 | 点对点 | 轨道 | 自主 |
| --- | --- | --- | --- |
| 终点谁定 | 人 / 上层业务 | 人（一串点） | 人 |
| 路径谁定 | 规划器，取最短或代价最低 | 人，预先录制或配置 | 机器人，运行时现算 |
| 意外谁管 | 基本没人管 | 靠局部避障兜底 | 规划器重规划 |

换句话说：

- **点对点：终点是输入，路径是副产品。** 你只关心到没到，不关心中间怎么绕。
- **轨道：终点和路径都是输入。** 你说走这条线，它就只走这条线。
- **自主：终点是输入，路径是输出，而且随时会变。** 你给它目标，剩下的它自己看着办。

这里有个特别容易踩的坑：「点对点」这个词在不同层指的不是一回事。

底盘 REST 接口里的 `move_to_location`，是底盘自己想办法过去，通常只有一圈超声或激光做局部避障，没有全局地图，也没有全局规划。而 ROS 2 里 Nav2 的 `NavigateToPose`，背后是定位、代价地图、全局规划、局部控制一整套链路——它虽然是「点对点」的接口形态，本质已经属于自主导航。

所以看到「点对点」三个字，先追问一句：**谁在规划？** 这一问能省掉后面很多扯皮。

## 三、点对点导航：你只说终点

点对点的定义很朴素：给一个目标位姿（`x`、`y`、`yaw`），机器人自己到那儿。

接口形态常见三种：

1. 底盘私有接口，比如 REST 的 `move_to_location`，或者串口协议；
2. ROS 2 标准 Action，比如 `nav2_msgs/action/NavigateToPose`；
3. 自己封一层语义接口，比如我们项目里的 `NavigateTo(poi)`——上层只说「去 POI_02」，坐标由底盘服务端查。

在终端里发一个标准目标长这样（在已启动 Nav2 的机器上执行）：

```bash
ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose \
  "{pose: {header: {frame_id: map}, pose: {position: {x: 3.2, y: -1.5, z: 0.0}, orientation: {w: 1.0}}}}" \
  --feedback
```

内部链路的最小版本是四步：**定位拿到当前位姿 → 全局规划出一条路径 → 局部控制跟踪这条路径 → 输出速度给底盘**。少了任何一步，都会退化成「朝着目标直冲」。

点对点什么时候够用？场地开阔、两点之间没有「必须绕开」的区域，点位稀疏、走一次算一次，或者只是演示、临时挪个位置、去某处看一眼——这些场景下，点对点是最省事的选择，几十行代码就能跑起来。

那什么时候翻车？我在项目里踩过两个，都很典型。

**第一，距离一长就失败。** 底盘对跨较大范围的点对点规划会直接返回失败——不是走得慢，是压根规划不出来。所以我们不能想当然地认为「去程怎么走，返程反过来走就行」，返程必须单独配一条轨道。

**第二，它走的是它认为最短的路，不是你想让它走的路。** 中间有刚拖过的湿地、临时堆的箱子、不该进的通道，它一概不知道。点对点没有「业务约束」这个概念，只有「几何上能不能过」。

还有一点：出问题你只能看结果。到没到、用了多久，中间怎么绕的、在哪儿卡了一下，日志里基本没有。调试的时候你会很想念轨道——至少轨道知道「本来该在哪」。

> **点对点是「能到就行」的方案。适合当积木，不适合当流程。**

## 四、轨道导航：路径是人给的

轨道导航反过来：路径是预先定好的，机器人只负责沿线走，到点停。

「轨道」不一定真是地上的铁轨，工程上有四种常见形态，差别很大：

| 形态 | 怎么来的 | 优点 | 代价 |
| --- | --- | --- | --- |
| 物理轨道 | 磁条、色带、反光板，传感器跟线 | 极稳、便宜、不依赖地图 | 改路线要动土，分叉麻烦 |
| 二维码 / 标签 | 地面贴码，扫到就校正位姿 | 定位准、部署快 | 码脏了磨了就丢，要长期维护 |
| 录制回放 | 人工遥控走一遍，录速度指令或轨迹，之后回放 | 上手最快，半天能用 | 环境一变就废，误差会累积 |
| 航点序列 | 在地图上标点，规划器把相邻点连起来 | 好改、可参数化、能配停留时间 | 依赖地图和定位质量 |

我们项目用的是第四种：一组 POI 点位 + 两条轨道（`tracks.outbound` 去程、`tracks.return` 返程）+ 每个点位的停留时间。POI 的坐标和朝向以底盘服务端为准，ROS 2 侧不再存一份，避免两边对不上。

为什么巡检场景爱用轨道？不是技术落后，是业务属性决定的。消防设施就在那几个位置，巡检本来就要按顺序走，这时候让规划器自由发挥反而是风险；轨道还能保证今天和下周走的是同一条线，出了问题能对比、能复盘；窄通道里规划器经常因为膨胀半径把路堵死，轨道没这个问题，因为路是人验证过的。

更实际的一点是现场能改：加个点、挪个点、改个停留时间，改配置就行，不用改代码、不用重新标定。这一点在验收阶段特别值钱，甲方说「这个点再往左半米」，你五分钟就能改完。

代价也很实在：

- **环境变了要重录。** 轨道是需要维护的资产，货架挪了、通道封了，轨道就废了。
- **被挡住不会自己绕。** 要么停在那儿等人，要么配局部避障——而避障之后怎么回到轨道上，是整个方案里最难的一段。
- **轨道和地图不一致时，表现为「看着到了，其实差 20 厘米」。** 这种问题最难查，因为每一步都「成功」了。
- **轨道质量决定上限。** 录制时手抖一下，回放时就偏；录制速度太快，回放时转弯就画龙。

这里有个我们实际踩到的坑，值得单独说：**到点 ≠ 朝向对。**

底盘固件会忽略 `move_to_locations` 里目标位置的 `yaw` 字段。也就是说，轨道导航把机器人送到点位了，位置没问题，但朝向可能是歪的。而消防设施可能在侧前方，朝向不对，后面的视觉检查直接废掉。

我们的处理是：到点后单独执行一次原地转向，转向完回读实际位姿做校验；误差超过阈值重试一次，还不行就把这次导航判为失败，不让机器人带着错误姿态进入下一个环节。

**位置精度和朝向精度是两件事，别指望一个接口同时给你。**

## 五、自主导航：路径在现场算

自主导航最容易被误解成「没有轨道」。准确的说法是：**不是没有轨道，是轨道在运行时才生成。**

它通常由四件套组成：

1. **地图与定位**：`map → odom → base_link` 这条变换链，AMCL 或激光惯性融合给出 `map → odom`，轮速和 IMU 给出 `odom → base_link`；
2. **感知与代价地图**：激光、深度相机、超声的点云打进 costmap，障碍物层标出「有东西」，膨胀层标出「离它多远算危险」；
3. **规划**：全局规划器（A*、Dijkstra、Hybrid-A*、状态格）出一条粗路径，局部规划器（DWB、TEB、MPPI、纯跟踪）负责跟踪并实时躲闪；
4. **恢复行为**：规划不出来的时候清代价地图、原地转一圈、往后退一点、等几秒再试。

膨胀半径是这里最需要现场调、也最容易被忽略的参数，Nav2 的参数文件里大概长这样：

```yaml
local_costmap:
  local_costmap:
    ros__parameters:
      robot_radius: 0.35
      inflation_layer:
        inflation_radius: 0.55
        cost_scaling_factor: 3.0
```

调大一点，机器人离障碍物更远、更安全，但窄门就过不去了；调小一点能挤过去，代价是剐蹭概率上升。这个值没有标准答案，只能拿卷尺量着场地试。

回到那个关键问题：自主和点对点是什么关系？

> **点对点是接口，自主是能力。**

`NavigateToPose` 这个「点对点」接口背后，跑的就是自主导航整套东西。所以「我们用了点对点导航」这句话，什么信息量都没有——它只说明接口长什么样，没说明谁在算路径。

自主导航真正的难点，从来不是「能不能走」：

- **能走 ≠ 走得稳。** 窄门、玻璃、镜面、地毯边缘、动态行人，每一个都能让局部规划器抽风。
- **能走 ≠ 可解释。** 为什么绕这么大一圈？为什么在这个位置停住不动？costmap 里那块「幽灵障碍」是哪来的？答不上来，现场就没法修。
- **能走 ≠ 可复现。** 同一个点，早上一次成功，下午三次失败，而你手里没有可对比的数据。
- **能走 ≠ 安全。** 规划器只知道「这儿能过」，不知道「这儿不该过」。

说白了，自主导航的工程量，八成花在**让它失败得可预期**上，而不是花在让它成功上。

## 六、同一台机器人身上，三种模式怎么共存

选型只是一半问题。真实系统里更麻烦的是：它们同时存在时，怎么不打架。

我们最后的层次是这样的：

```text
上层编排（巡检流程）
        │  NavigateTo(poi)
        ▼
导航服务端 ── 模式管理：轨道 / 点对点 / 避障
        │
        ├─► 轨道接口（底盘 REST）
        ├─► 局部避障（激光 / 超声）
        └─► 安全层（限速 / AEB / 急停）
```

三个约束，是这套东西能跑起来的前提。

**第一，同一时刻只允许一个运动任务。** 轨道在走的时候来一个点对点目标，必须拒绝或者排队，不能两路速度指令同时往底盘塞——底盘不会帮你仲裁，它只会听最后一条。

**第二，模式必须是分层的，不是并列的。** 轨道负责「这一段怎么走」，点对点负责「去哪」，避障负责「这一秒怎么躲」。层与层之间只能通过状态机交互，不能让避障直接改轨道进度。

**第三，切换必须有前置条件和清理动作。** 避障触发时要暂停轨道进度，避障结束要重新确认位姿、判断是否还在轨道上，然后才能恢复。少了这一步，就会出现「避让完成、位置变了、进度还停在原来那一段」的错乱。

状态机大概长这样：

```text
IDLE ──goal──► MOVING（轨道 / 点对点）
                  │ 检测到障碍
                  ▼
              AVOIDING ──完成──► RECOVERING
                  │                  │ 重新定位、校验进度
                  │ 失败              ▼
                  └────────────► MOVING
                  │
                  ▼
              STOPPED（等人工）
```

另外，上层必须能看见当前模式。我们的导航 Action 在 Feedback 里带了「当前导航阶段、导航模式、剩余距离」三个字段——不是为了好看，是因为现场排障时，第一句话永远是「它现在在干嘛」。

## 七、三者是一条连续谱，不是三选一

把三种方式摆在一起比工程代价：

| 维度 | 点对点 | 轨道 | 自主 |
| --- | --- | --- | --- |
| 路径约束 | 无 | 强 | 弱，靠代价地图约束 |
| 结果确定性 | 低 | 高 | 中 |
| 环境适应性 | 差 | 差 | 好 |
| 调试难度 | 低 | 中 | 高 |
| 部署成本 | 低 | 中 | 高 |
| 换个场地 | 改坐标 | 重配轨道 | 重建地图 |

从「路径被人约束的强度」看，它们是一条连续谱：点对点几乎不约束路径，轨道把路径完全钉死，自主把路径交给运行时生成、并且允许走一步看一步。约束越少，机器人越自由，也就越难保证它按你的想法走。

真实项目里，几乎没有纯的。我们的架构就是混着的：主干用轨道，因为巡检路线固定、业务要求可复现；点位切换用点对点，本质是一次短距离点对点；局部用避障兜底；安全层独立，不依赖任何规划器——规划器可以出错，刹车不能。

这也是大多数工业机器人的形态：**路线级用轨道，路段级用自主。**

所以「该选哪个」这个问题，其实有个很实用的判断法：

> **现场有没有人能说清楚「必须经过哪几个点」？能，就用轨道；说不出，才轮到自主。**

如果连「从哪儿走比较安全」都没人答得上来，那自主导航也很难救——它只是把不确定性从人的脑子里，挪到了 costmap 里。

## 八、真正决定成败的五个细节

这三个词怎么分，其实只影响选型。真正让项目上线或者翻车的，是下面这些不分类型的东西。

**1. 位姿从哪来。** 所有导航的共同敌人是定位漂移。定位跳一下，三种导航一起完蛋，而且症状各不相同：点对点会走歪，轨道会越走越偏，自主会把机器人送进墙里。所以我们实机模式运动前必须检查定位状态，定位异常直接拒绝执行；模拟模式不下发真实运动，只告警。

**2. 到点不等于到位。** 位置误差 5 厘米、朝向误差 30 度，视觉模块就白干了。位置和朝向要分开校验、分开重试，别用一个成功标志糊弄过去。

**3. 速度是安全参数，不是性能参数。** 我们巡检和返程都限 0.4 m/s。写限速还有个细节：写入后必须回读确认，失败就回滚原值；节点退出时恢复备份。**写进去不等于生效**，这个道理在底盘上尤其成立。

**4. 失败路径比成功路径重要。** 超时、取消、定位丢失、底盘故障、网络中断——每一类都要能回答：停在哪、状态怎么清、上层怎么知道。我们的顺序是固定的：取消底盘动作 → 停车 → 关 AEB → 上报结果。顺序错了，就会出现「以为停了其实还在动」这种最危险的情况。

**5. 数据只能有一份。** POI 坐标如果同时存在底盘服务端、ROS 2 配置和巡检流程里，早晚对不上，而且对不上的时候通常没人知道是哪一份错了。我们定死以底盘为准，其他位置全部引用。

## 九、五个常见误区

**「自主导航就是不用地图。」** 反了。自主最吃地图质量——地图脏，代价地图就脏，规划就抽风。地图是自主的地基，不是可选项。

**「轨道导航没什么技术含量。」** 轨道本身不难，难在维护和异常：轨道漂移、被临时物体挡住、避障之后怎么回轨、轨道和地图不一致怎么查。这些活一点也不比调规划器轻松。

**「点对点就是自主导航。」** 取决于谁在规划。底盘侧的 `move_to_location` 通常只有局部避障；Nav2 的 `NavigateToPose` 才是完整链路。同一个词，两套系统。

**「避障就是绕开。」** 避障是「停 → 看 → 绕 → 回」一整段状态机。绕完不回到原任务、不重新确认位姿，等于白绕，甚至会跑到轨道外面去。

**「定位好了就哪都能去。」** 定位是必要条件，不是充分条件。还有通道宽度、膨胀半径、底盘转弯半径、地面摩擦系数，任何一个不满足，定位再准也过不去。

## 十、怎么验收：三种方式三套指标

验收标准选错，最后一定会变成「看着还行」。三种导航的验收口径完全不同：

| 方式 | 主指标 | 辅助指标 | 怎么测 |
| --- | --- | --- | --- |
| 点对点 | 到达成功率 | 平均耗时、实际路径长度 | 同一个点重复跑 20 次 |
| 轨道 | 到点位置误差 / 朝向误差 | 轨迹偏离、停留时长 | 卷尺量 + 日志回放 |
| 自主 | 成功率 + 人工接管次数 | 重规划次数、恢复触发次数 | 不同时段、不同人流重复跑 |

自主导航尤其要看「接管次数」。成功率 95% 听起来不错，但如果每 20 次里有 1 次要人跑过去把机器人拽出来，这个系统在真实场景里就是不可用的——因为接管的那一次通常发生在最不方便的时候。

## 十一、怎么选：一张决策表

| 场景 | 建议 | 原因 |
| --- | --- | --- |
| 固定路线巡检、点检 | 轨道 + 点位 | 可复现、可维护、现场能改 |
| 仓储搬运，货架到货架 | 拓扑路线 + 局部自主 | 主通道固定，末端要灵活 |
| 开阔场地临时去某点 | 点对点 | 一条指令搞定，不值得上全套 |
| 家庭 / 办公服务机器人 | 自主 | 环境天天变，没法预录 |
| 跨楼层、跨区域长距离 | 分段 + 轨道 | 长距离点对点容易规划失败 |
| Demo、演示 | 点对点 | 最快出效果 |

这张表不是标准答案，但它背后的逻辑是稳的：**路线越固定、现场越难改，越往轨道靠；环境越不可控、点位越随意，越往自主靠；只有一个终点、路况又开阔，点对点最省事。**

## 十二、一句话总结

三种导航不是三代技术，是三种约束程度：

- **点对点**：只约束终点，路径随便，最省事也最不可控；
- **轨道**：终点和路径都约束，最死板也最可复现；
- **自主**：只约束终点，路径现场算，最灵活也最难调。

真到了项目上，别纠结「该用哪个」，先问三个问题：

1. 现场有没有人说得清「必须经过哪几个点」？
2. 出了问题，需不需要复盘「它当时为什么这么走」？
3. 环境一个月会变几次？

第一个答「有」，就上轨道；第二个答「需要」，也上轨道；第三个答「经常变」，再补自主那一层。三个都答不上来，先做点对点，把流程跑通，别一上来就堆全套——那通常不是技术选型，是给自己找活干。
