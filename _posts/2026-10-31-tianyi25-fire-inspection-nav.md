## 一、项目背景

天轶 2.5 消防巡检项目面向室内消防设施巡检场景。机器人按照预设路线进行巡航，在指定点位停留，再配合视觉模块检查灭火器、消防设施和安全出口等目标，并通过语音模块播报巡检状态及异常信息。

在整个系统中，导航模块负责解决一个基础但关键的问题：

**机器人如何按照既定巡检顺序，从当前位置安全、可靠地到达指定点位，并在巡检结束后返回起点？**

我在项目中主要负责导航部分，工作重点包括：

- 根据消防巡检场景设计点位巡检流程；
- 对接机器人底盘提供的 POI 和轨道导航能力；
- 使用 ROS 2 Action 封装导航任务；
- 处理到点转向、停留、返程和任务取消等情况；
- 增加运动前检查、限速、避障相关处理和异常保护；
- 通过 dry_run 和实机测试逐步验证导航流程。

## 二、导航方案：预设轨道与固定点位结合

### 2.1 为什么采用轨道导航

室内消防巡检路线通常相对固定，巡检点位也比较明确。对于这种场景，使用预先配置的轨道和 POI（Point of Interest，兴趣点）组织路线，能够让巡检路径和点位顺序更加清晰，也便于现场调整。

本项目的导航不是简单地让机器人在地图上随意寻找一个坐标，而是结合底盘已有的 POI 服务和轨道能力完成路线执行：

- **POI 点位**：描述巡检起点、检查点和中转点；
- **轨道路线**：描述机器人在巡检路段或返程路段需要经过的航点；
- **点位顺序**：约束巡检任务的执行次序；
- **停留时间**：机器人到达检查点并完成朝向调整后，按配置停留，为后续检查留出时间。

项目中，点位坐标和朝向以底盘 POI 服务端为准，避免在 ROS 2 导航配置中维护另一份容易与实机地图不一致的数据。

### 2.2 巡检流程

整体导航过程可以概括为：

```text
开始巡检
   |
   v
前置检查
   |
   v
前往起点
   |
   v
按顺序访问巡检点位
   |
   +----> 到达目标点
   |          |
   |          v
   |       调整朝向
   |          |
   |          v
   |       停留等待检查
   |          |
   |          v
   |       前往下一个点位
   |
   v
巡检点位完成
   |
   v
沿返程轨道返回起点
   |
   v
任务结束
```

导航模块主要负责机器人移动和点位到达，不直接承担视觉识别、语音播报等业务。这样可以让各模块职责更加明确，也方便独立调试。

## 三、ROS 2 导航模块设计

### 3.1 工作空间与功能包划分

项目使用 ROS 2 Jazzy，主要采用 Python 和 `rclpy` 开发。导航功能位于 `fire_inspection_nav` 功能包，相关接口集中在 `fire_inspection_interfaces` 中。

工作空间的核心功能包包括：

| 功能包 | 主要职责 |
| --- | --- |
| `fire_inspection_interfaces` | 定义项目内部使用的 msg、srv 和 action 接口 |
| `fire_inspection_nav` | 导航 Action 服务端，对接底盘并执行点位导航 |
| `fire_inspection_vision` | 负责巡检点位的视觉检查 |
| `fire_inspection_voice` | 负责语音播报 |
| `fire_inspection_head` | 负责机器人头部扫视 |
| `fire_inspection_orchestrator` | 负责组织巡检流程和调用各功能模块 |

这种划分使导航模块可以独立启动和测试。上层流程只需要发送导航目标，不需要了解底盘 REST API 的具体调用细节。

### 3.2 为什么使用 Action 封装导航任务

导航通常不是一个瞬间完成的操作。从发送目标到机器人实际到达，中间可能持续数秒甚至更长时间，并且需要反馈当前执行状态，还要支持取消。

因此，项目使用 ROS 2 Action 定义导航任务 `NavigateTo`，而不是使用一个需要等待移动完成的同步 Service。

Action 主要包含三个部分：

- **Goal**：指定需要前往的 POI，以及是否属于返回起点任务；
- **Feedback**：反馈当前导航阶段、导航模式和剩余距离等信息；
- **Result**：返回任务是否成功、是否取消以及执行结果说明。

在终端中，可以通过以下命令向导航 Action 发送目标：

```bash
ros2 action send_goal \
  /fire_inspection/navigate_to \
  fire_inspection_interfaces/action/NavigateTo \
  "{poi: 'POI_01'}" \
  --feedback
```

返回起点时，需要明确设置 `is_return`：

```bash
ros2 action send_goal \
  /fire_inspection/navigate_to \
  fire_inspection_interfaces/action/NavigateTo \
  "{poi: 'start_point', is_return: true}"
```

通过 Action，调用方不必阻塞等待整个导航任务结束，可以在执行过程中接收反馈，也可以在必要时取消任务。

## 四、导航执行中的关键问题

### 4.1 点位顺序管理

消防巡检不是任意点位之间的自由跳转，而是有明确的执行顺序。因此，导航模块需要维护当前巡检进度，并检查新目标是否符合预定顺序。

例如：

```text
start_point
    |
    v
  POI_01
    |
    v
  POI_02
    |
    v
  POI_03
    |
    v
返回 start_point
```

如果当前应该前往 `POI_02`，却重复请求 `POI_01`，导航服务端应拒绝该目标并返回明确原因，而不是继续执行错误路线。

同时，还需要考虑以下情况：

- 尚未开始巡检时，不允许直接执行返程；
- 已经在起点时，不应重复执行无意义的返程；
- 中途返程后再次开始巡检时，应正确处理已有进度；
- 一轮巡检完成并返回起点后，应允许开始新一轮任务；
- 同一时刻只接受一个导航目标，避免多个运动任务相互冲突。

这些检查能够减少错误指令对机器人实际运动的影响。

### 4.2 巡检轨道与返程轨道

项目将巡检轨道和返程轨道分别配置。巡检时沿 `tracks.outbound` 前进，返回起点时沿 `tracks.return` 行驶。

这里有一个实际调试中需要注意的问题：底盘对于跨越较大范围的点对点返程规划可能失败，因此不能简单地认为“去程怎么走，返程反过来走”就一定可行。需要结合底盘的实际规划能力配置专门的返程轨道。

### 4.3 到点后的朝向调整

机器人到达巡检点位，并不意味着导航任务已经完全结束。消防设施可能位于机器人正前方或侧前方，如果到点后的朝向不合适，会影响后续视觉检查。

项目在轨道导航到点后，会根据 POI 的目标朝向执行原地转向，并回读实际位姿进行校验。

需要注意，当前底盘固件会忽略 `move_to_locations` 中目标位置的 `yaw` 字段，因此不能只依赖轨道导航自动完成朝向调整。导航模块需要在必要时额外执行转向，并检查转向结果。

如果实际朝向与目标朝向的误差超过设定阈值，则进行一次重试；仍然不符合要求时，将该导航任务判定为失败，避免机器人以错误姿态进入后续巡检环节。

### 4.4 到点停留

到达巡检点位并完成转向后，机器人需要停留一段时间，为视觉检查和其他巡检操作提供条件。

项目支持配置默认停留时间，也允许针对不同 POI 设置单独的停留时间。起点和返程点则不需要按照普通巡检点的方式停留。

停留过程也需要响应取消请求，不能因为进入等待阶段就失去任务控制能力。

## 五、底盘对接与运动安全

### 5.1 通过底盘 REST 接口执行运动

导航服务端通过底盘提供的 REST API 与机器人底盘交互，默认服务地址为：

```text
http://192.168.11.10:9090
```

导航模块负责把 ROS 2 层的 POI 导航请求转换成底盘能够识别的运动操作，并读取底盘动作状态，判断当前运动是否已经结束。

这种方式将上层 ROS 2 任务接口和底盘实际控制接口隔离开来。上层只需要关注“去哪个点位”，底层则负责完成具体运动和状态检查。

### 5.2 运动前检查

机器人运动前必须确认基础状态正常。项目实机模式下会检查定位状态和底盘健康状态：

- 定位状态异常时拒绝执行运动目标；
- 底盘存在需要阻止运动的故障时拒绝执行，并输出相关故障信息；
- POI、轨道和相关配置通过前置检查后，才允许继续执行导航任务。

模拟模式与实机模式的检查策略有所区别：模拟模式不下发真实运动指令，因此定位异常可以告警；实机模式则必须严格通过定位检查。

### 5.3 限速与 AEB 保护

实机运动前，导航模块会读取并备份底盘原有速度限制，再按照巡检和返程配置设置速度。默认巡检与返程速度均为 `0.4 m/s`。

限速设置不能只写入而不验证。项目会在写入后回读确认；如果写入或验证失败，则回滚原值并终止当前操作。节点退出时也会恢复此前备份的速度配置，尽量避免影响底盘其他任务。

每段运动开始前还会开启 AEB。运动过程中持续轮询底盘动作状态，直到动作进入终态。如果出现失败、超时或取消，则按顺序取消底盘动作、停车，再关闭 AEB。

这部分逻辑的重点不是让机器人尽可能快地完成路线，而是确保运动过程可检查、可停止，并且出现异常时有明确的处理路径。

## 六、避障功能的调试与优化思路

在实际项目调试中，除了正常轨道行驶，还需要考虑巡检过程中出现的障碍物，以及吸烟行为检测等异常场景。

围绕这些情况，我对导航过程中的避让策略进行了迭代尝试，主要关注：

1. **前方障碍物避让**：当机器人前方存在障碍时，不能只考虑继续向目标点移动，需要结合现场情况采取避让或停止策略。
2. **异常行为触发的避让**：在吸烟行为检测等场景中，尝试让机器人执行侧移避让，再继续前往后续目标点。
3. **避让后的任务衔接**：避让动作结束后，需要确认机器人状态和当前位置，再决定是否继续原导航任务，避免出现避让完成但巡检流程状态不一致的问题。

避障不是简单增加一个“向左或向右移动”的动作。真正需要处理的是障碍物出现、避让执行、状态确认、恢复导航这一整段流程。

目前这些策略仍需要结合实机环境持续测试和优化。尤其是侧移距离、障碍物位置、轨道边界和避让后的路径衔接，都需要通过实际数据确定，不能仅凭单次运行结果判断策略已经完善。

## 七、导航模块的测试方式

为了降低实机调试风险，项目提供了 `dry_run` 模式。

### 7.1 dry_run 模式

先启动导航服务端：

```bash
ros2 launch fire_inspection_nav navigate_to.launch.py
```

再通过 Action 命令依次发送目标：

```bash
ros2 action send_goal \
  /fire_inspection/navigate_to \
  fire_inspection_interfaces/action/NavigateTo \
  "{poi: 'start_point'}" --feedback

ros2 action send_goal \
  /fire_inspection/navigate_to \
  fire_inspection_interfaces/action/NavigateTo \
  "{poi: 'POI_01'}"

ros2 action send_goal \
  /fire_inspection/navigate_to \
  fire_inspection_interfaces/action/NavigateTo \
  "{poi: 'POI_02'}"

ros2 action send_goal \
  /fire_inspection/navigate_to \
  fire_inspection_interfaces/action/NavigateTo \
  "{poi: 'POI_03'}"
```

模拟模式下可以重点检查：

- 点位顺序是否正确；
- 非法目标是否被拒绝；
- 返程条件是否正确；
- Action Feedback 和 Result 是否符合预期；
- 取消和超时是否能够正常处理。

`dry_run` 的意义是先验证任务逻辑，避免每次修改都直接让机器人执行真实运动。

### 7.2 实机测试

实机测试前需要完成定位，并确认底盘状态正常。项目提供了导航启动脚本：

```bash
/home/nvidia/fire-inspection/run_nav.sh
```

如果只想执行检查而不让机器人运动，可以使用：

```bash
/home/nvidia/fire-inspection/run_nav.sh --dry-run
```

首次实机测试应保持低速、空载、有人现场守护，并确保急停装置随时可用。测试时重点观察：

- 机器人是否沿预定轨道运动；
- 是否准确到达目标点位；
- 到点后的朝向是否正确；
- 停留时间是否符合配置；
- 返程是否沿专用轨道完成；
- 发生取消、超时或底盘异常时，机器人能否及时停止。

## 八、开发过程中的问题与收获

通过导航模块的开发和调试，我对机器人导航的理解不再停留在“给一个目标点，机器人移动过去”。

一个完整的导航任务还需要考虑任务顺序、底盘状态、运动速度、定位质量、目标朝向、停留时间、取消机制以及异常恢复。

这次开发中，我认为有几个比较重要的经验：

**第一，ROS 2 接口设计要符合任务特点。** 导航是持续执行的长任务，使用 Action 可以自然地表达目标、过程反馈和最终结果，也方便上层编排模块统一调度。

**第二，配置数据要有明确的唯一来源。** POI 坐标和朝向直接以底盘服务端为准，避免多个模块各自维护一份数据，导致地图和程序配置不一致。

**第三，模拟测试和实机测试要分层进行。** 先通过 dry_run 验证点位顺序、状态流转和异常处理，再进行低速实机测试，能够减少不必要的运动风险。

**第四，运动控制必须考虑失败路径。** 超时、取消、底盘故障和定位异常都不是少见的边界情况。导航模块不仅要处理正常到达，也要保证失败时能够停车并清理状态。

**第五，避障需要和任务流程结合。** 避让动作本身并不等于导航恢复。需要在避让后重新确认机器人状态和目标关系，才能安全地继续执行任务。

## 九、后续优化方向

导航模块仍有继续完善的空间，后续可以重点推进：

1. **完善避障策略**：继续优化前方障碍物和异常行为触发后的侧移避让，重点验证避让距离、恢复条件和路径安全性。
2. **提高异常恢复能力**：针对定位丢失、底盘动作失败、通信中断等情况，完善状态检查和恢复流程。
3. **加强实机验证**：在不同障碍物位置、不同巡检点位和不同网络状态下进行多轮测试，记录成功率和异常情况。
4. **完善导航与巡检流程协作**：进一步明确导航到点、视觉检查、语音播报和返回起点之间的状态衔接。
5. **整理测试记录与参数**：将典型问题、参数调整和验证结果沉淀下来，便于后续维护和团队协作。

## 十、总结

天轶 2.5 消防巡检机器人的导航模块，是连接机器人底盘运动能力和上层巡检业务流程的重要部分。

在这个项目中，我主要围绕预设轨道、固定 POI、ROS 2 Action 和底盘 REST 接口完成导航功能设计与调试，并逐步完善点位顺序检查、到点转向、停留、返程、限速、AEB 和异常处理等机制。同时，也针对障碍物和异常行为场景开展了避让策略的优化尝试。

这次开发让我认识到，机器人导航不仅要关注能不能到达目标点，更要关注任务是否按照预期执行、运动过程是否安全，以及出现异常后能否可靠地停止和恢复。后续还需要通过更多实机测试，不断提升导航模块在真实消防巡检场景中的稳定性。
