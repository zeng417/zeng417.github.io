## 一、项目背景

天轶 2.5 消防巡检项目面向室内消防设施巡检场景。机器人按预设路线巡航，在指定点位停留，配合视觉模块检查灭火器、消防设施和安全出口，再通过语音模块播报状态和异常。

导航模块要解决的问题看起来很简单：

**机器人如何按既定顺序，从当前位置安全、可靠地到达指定点位，巡检结束后再返回起点？**

但真做下来，这句话里藏着四件事：**顺序**（不能想去哪就去哪）、**到位**（到了不等于站对了）、**中断**（随时可能被叫停或被人挡住）、**回来**（返程往往比去程更难）。

我在项目里负责导航部分，具体工作包括：

- 设计巡检点位顺序和停留策略；
- 把底盘的 POI / 轨道能力封装成 ROS 2 Action；
- 处理出发朝向、到点转向、到点校验、停留、取消、超时；
- 实现受阻后的自恢复，以及返程被打断后的续行；
- 加运动前检查、限速、AEB、软限位和走廊校验；
- 用 dry_run、单元测试和实机测试分层验证。

在系统里，导航只是「一段运动」的执行者。整个巡检流程由 `fire_inspection_orchestrator` 统一指挥，导航、视觉、语音、头部之间不允许互相调用。这条约束在后面会反复出现——它决定了导航在遇到问题时该「自己扛」还是「上报」。

## 二、方案：轨道为主，点对点为辅

### 2.1 为什么不全自主

室内消防巡检的路线高度固定，点位也明确。项目用的是底盘自带的 POI 和轨道能力，没有另外搭一套 SLAM 和全局规划器。

理由很实际：这套场景里，「能到」比「能自由地到」更重要。自建导航栈意味着定位、代价地图、局部规划、恢复行为全套都要自己调，而在一条固定走廊里，这些复杂度换不来多少收益。

代价是灵活性差。所以方案里留了点对点作为补充：起点集合、返程上轨点、绕行之后重发目标，这些场景走点对点；巡检主路段走轨道。

> 点对点、轨道、自主导航三者的区别和适用边界，我另外写过一篇：[点对点、轨道与自主导航：三种「自己走过去」到底差在哪](https://zeng417.github.io/posts/robot-navigation-modes/)。这里只讲落地。

### 2.2 点位与轨道怎么组织

所有导航参数集中在一个文件里：`src/fire_inspection_nav/config/pois.yaml`。它是导航的唯一配置源，代码里不写死任何点位。

```yaml
poi_source: chassis          # 点位坐标以底盘 POI 服务为唯一真源
start_poi: start_point
poi_order: [POI_01, POI_02, POI_03, POI_04]
transit_pois: [POI_04]       # 只过点不上巡检轨道，同时是返程上轨点

tracks:
  outbound: track_line_1000  # 巡检段
  return: track_line_1001    # 返程段

dwell_s: 5.0
dwell_overrides:
  POI_01: 1.0
  POI_02: 1.0
  POI_03: 1.0
  POI_04: 3.0

speed:
  outbound_mps: 0.4
  return_mps: 0.4

arrival_tolerance_m: 0.5
yaw_overrides:
  POI_03: -1.5708
```

几个刻意的设计：

- **坐标和朝向以底盘为准**。ROS 侧只维护「顺序、停留时长、朝向覆盖、超时（每段 180 秒）」，不复制一份坐标。两份数据一旦不一致，排查成本极高。
- **巡检轨道和返程轨道分开配置**。底盘对跨越大范围的点对点规划并不可靠，返程必须走专用轨道（原因见第五节）。
- **`POI_04` 是「过点」**。它在 `transit_pois` 里，默认走点对点、到点不停留，同时也是返程轨道的上轨点。
- **停留时长按点位覆盖**。全局默认 5 秒，实际配的是 1 秒（视觉抓拍够了），`POI_04` 给 3 秒，起点不停留。

### 2.3 巡检流程

```text
开始巡检
   |
   v
前置检查（POI/轨道/定位/健康/软限位）
   |
   v
点对点前往起点 start_point
   |
   v
沿巡检轨道 track_line_1000 依次到 POI_01 → POI_02 → POI_03
   |                                        |
   |                          到点：补转朝向 → 校验位置 → 停留
   v
点对点前往 POI_04（返程上轨点）
   |
   v
沿返程轨道 track_line_1001 返回起点
   |
   v
任务结束
```

中途任何一段都可能被打断：控制台暂停、人工急停、视觉发现吸烟行为要求侧移。导航要保证的是——**打断之后还能接着走**，而不是从头再来。

## 三、接口：四个 Action，一套「可解释」的契约

### 3.1 NavigateTo：把「去哪」和「怎么去」分开

导航任务用 Action 而不是 Service，因为它是长任务：有过程、有反馈、可取消。

```text
# goal
string poi            # 目标点位名
bool   is_return      # 是否返程
float64 timeout_s     # 本段超时
bool   use_point      # true = 强制点对点，不用轨道

# feedback
string phase          # navigating | arrived | detour
string mode           # point | track
float64 distance_remaining_m

# result
bool   success
bool   is_return      # 回显，防止上层串味
string message        # 给人看的说明，含进度快照
string phase          # arrived | failed | cancelled | blocked
```

两个细节值得说。

第一，**`is_return` 必须显式给，不做意图猜测**。早期想过「目标是 start_point 就自动当返程」，很快放弃了：去起点集合和巡检结束回起点，语义完全不同，前者走点对点，后者必须走返程轨道。让调用方写清楚，比让服务端猜可靠一万倍。

第二，**`blocked` 是一个独立的终态**。它不表示「导航挂了」，而表示「这段路我过不去，但车是安全的、停稳的、状态是干净的」。这两个语义差别很大：`failed` 会让上层判整轮失败，`blocked` 允许上层跳过这个点继续巡检。把「我失败了」和「我被卡住了」分开，是这套接口里最值钱的一个决定。

反馈里的 `phase` 也有讲究。判定受阻的瞬间就发 `detour`，而不是等绕行做完再发——编排层拿到这个相位，可以在车还停着的时候播报「前方有障碍，正在尝试绕行」，现场听感完全不同。

### 3.2 ApproachTarget：不给坐标，给方位角和距离

吸烟行为检测触发后，机器人要走到人员前方约 2 米处，侧偏 1.2 米，方便正面劝导。

视觉模块能给什么？它给不了地图坐标——画面里只有「人在画面偏左 20 度、距离大约 4 米」。所以接口设计成相对量：

```text
# goal
float64 bearing_rad    # 正 = 目标在左，负 = 在右
float64 range_m        # 估计距离
float64 standoff_m     # 停在目标前方多远
float64 side_offset_m  # 侧偏，避免正对堵死
float64 timeout_s

# result
string  phase          # arrived | skipped | failed | cancelled
float64 final_range_m
```

导航服务端拿到这三个数，结合当前位姿在本地算出落点（`compute_approach_geometry`），再用点对点过去。这样做的原因是：视觉的深度估计有误差，地图坐标也有漂移，两个不准的东西相乘，结果更不准；而「往左转 20 度、走 4 米」是一个闭环，走一步看一眼，误差不累积。

距离太近（<2m）或太远（>10m）直接 `skipped`，不让机器人为了一个不可信的目标乱动。到达后如果最后距离和期望差得多，只告警不判失败——这是「尽力而为」的动作，不是巡检点。

### 3.3 一次一个目标

同一时刻只接受一个导航目标，新目标来了先拒绝。顺序校验也在这里：该去 `POI_02` 的时候请求 `POI_01`，直接返回明确原因，不执行。

看起来是小事，但现场调试时，一个乱序的目标能让机器人往回走十几米，而操作员往往以为是「导航算错了」。

### 3.4 另外两个接口

`InspectPoi` 在点位触发视觉检查，状态分得比导航还细：正常、异常、不确定、超时、没有画面、没有模型、内部错误，还带 `simulated` 标记防止模拟数据混进真实记录。`Speak` 管播报，支持打断。导航不直接调这两个——它只发 `arrived`、`blocked` 这类相位，播什么、什么时候播，由编排层决定。

## 四、真正花时间的地方：离点和到点

### 4.1 出发前先转正，否则车是「横着跑」的

这是最早踩的坑，也是最容易被忽略的。

底盘的轨道接口只负责「沿轨道走」，**不会自动把车头转到行进方向**。如果上一条轨道的末端朝向和下一条轨道的起始方向差 90 度（`POI_02 → POI_03` 就是），车会保持原来的朝向，横着平移过去。现场看着像机器人「侧着身子飘」，视觉画面全歪，到点补转也救不回来。

点对点也有类似问题，只是表现不同：固件默认「边转边移」，车头背对目标时会先画一个大弧，看起来像在绕圈。

处理方式是在下发运动前先原地对齐：

- 轨道段：把车头转到轨道起始方向，容差 `0.15 rad`；
- 点对点：把车头转向目标点，距离很近时（<0.4m）只转向不移动，避免原地蹭。

代价是每段多花一两秒。但和「横着跑过去再横着回来」相比，这个时间花得值。

### 4.2 「动作成功」不等于「到了」

底盘返回 success，只代表它把这段动作执行完了，不代表车停在巡检点上。定位漂移、轨道提前结束、被障碍物顶偏，都会让车停在离目标一两米的地方，而接口依然报成功。

所以到点后要做两道校验：

```text
位置：|实际位姿 - POI 坐标| ≤ 0.5m，否则判失败
朝向：|实际朝向 - 目标朝向| ≤ 0.10 rad，否则重试一次，仍超限判失败
```

朝向校验还有个前提问题：**固件会忽略 `move_to_locations` 里的目标 yaw**。所以轨道到点后必须自己补一次原地转向，再回读位姿确认。`POI_03` 的目标朝向是 -90 度，但地图里配的是 -60 度，两者不一致，只能靠 `yaw_overrides` 在导航侧覆盖——这也是「配置要有唯一来源」的一个反例：能覆盖，但要写清楚为什么覆盖。

还有个细节：车停稳后立刻发 `arrived` 反馈，不等转向和停留做完。因为编排层收到 `arrived` 才会停掉头部扫视，否则现场会出现「车已经到了、头还在左右扫」的诡异画面。

### 4.3 停留：默认值、覆盖值和「不停」

停留逻辑很简单，但规则要明确，否则会出现「过点也停 5 秒」这种浪费：

- 起点：0 秒；
- `dwell_overrides` 里有配置：用配置值；
- `transit_pois`（过点）：0 秒；
- 其余：全局 `dwell_s`。

停留期间每 100ms 检查一次取消请求，随时能停。这一点很重要——巡检停留是「等待」，不是「失去控制」。

## 五、和底盘固件打交道：三个「不能信」

这一节是全文最「脏」的部分，也是我认为最有价值的部分。文档写的语义和固件实际行为之间的差距，只能靠现场试出来。

### 5.1 不能信拒绝响应里的「剩余距离」

底盘拒绝一个动作时，返回体里会带 `distance_remaining` 和 `distance_time`。看起来很有用，实际上不可靠：一次现场记录里，机器人刚下发就失败，返回的剩余距离是 **10246mm**，剩余时间也是非零——单看字段，会以为「车已经跑了一大半然后失败了」。

真实情况是：车一动没动，拒绝发生在停稳过渡期。

所以判断「是不是瞬时拒绝」不能看固件字段，要看自己的观测：

```text
下发后 1.5s 内失败，且
  - 固件标记「从未起步」，或
  - 我方位姿观测位移 < 0.10m
=> 按瞬时拒绝处理：撤干净，等 1.0s，原样重发一次
```

实测被拒的时间是 **0.11s**，正好落在停稳过渡窗口里。重发一次基本都能过，而如果不做这个处理，一次误拒就会让整轮巡检中断。

### 5.2 不能信「轨道续行」的起点

返程被打断（比如有人站在轨道中间，机器人停车播报）之后，车停在轨道中间。此时想让车「从当前位置继续走返程轨道」，看起来天经地义。

固件不这么认为：`move_to_locations` 只接受从**上轨点**（`POI_04`）续行。传轨道中间的投影点作为起点，**0.11s 即 failed**，连续瞬拒。

试过几条路，都撞墙：

- 重发上轨续行 → 车掉头回 `POI_04`，现场表现就是「一播报就往回开」；
- 先点对点回到轨道中心线再续行 → 车绕一下又回到原地，和同一个人再次相遇；
- 一次性跨图点对点（16m）→ 底盘接受，但不产生位移。

最后的办法是**分段点对点**：沿返程轨道折线，每 4 米取一个落点，用点对点逐段推进，最多 10 段。每段都过一遍软限位和走廊校验，并且保持介入后的横向偏移——车被侧移到走廊一侧之后，沿轨道前进时不能立刻回中心线，否则又开回刚避开的人面前。

```text
while 未到目标:
    if 剩距 ≤ 4m: 落点 = 目标点
    else:         落点 = 沿返程轨道前方 4m 处的折线点
    落点 += 保持当前横向偏移（垂直轨道方向）
    点对点下发，等终态，校验位置
```

16 米的返程变成 5 段左右，每段都能独立失败、独立重试。慢一点，但可控。

### 5.3 不能信「跨图点对点」

这一点决定了整个方案的形状：**远距离点对点在这套底盘上不可用**。要么规划直接失败，要么接受但不走。

所以点对点只出现在三个地方：起点集合、去 `POI_04`、绕行后重发。而且绕行后的点对点兜底有个硬限制——**只有距目标 5 米以内才允许**。远处宁可判 `blocked` 让上层跳过，也不让车跨区直线乱窜。

「宁可失败，也不赌一把」，这条在移动机器人上通常是划算的，代价是偶尔会显得「明明能过去却停了」——但比冲到墙里强。

## 六、受阻自恢复：8 秒、0.1 米、两次机会

巡检现场最常见的故障不是报错，是「车不动了」：轮子卡住、前方有人站着、地上有货箱，接口一直返回「执行中」，没有任何异常。

导航侧要能自己发现这件事，并且尝试脱困。

**检测**只在平移段开启——原地转向时位置本来就不变，放在那里会把正常转向误判成受阻。判定条件：

```text
从「最近一次确认有位移」的位置起算
8 秒内位移 < 0.10m，且距目标 > 0.5m（到点容差）
=> 判定受阻
```

锚点跟着位移走，所以「慢慢挪」不会误报，「彻底卡死」才会触发。

**恢复**是一条固定链路，每次受阻按顺序执行：

```text
1. 取消当前底盘动作，等车停稳
2. 重新校验健康状态（不带故障倒车）
3. 后退 0.5m，速度 0.2m/s，最小安全间距 0.2m
4. 侧向绕行：第 1 次向左 1.0m，第 2 次向右 1.5m
   同侧挪不动就立刻换另一侧
5. 绕行后重发原目标（已离开轨道，改点对点直奔点位）
```

如果后退失败（后面也堵死），不急着放弃：先原地转 45 度换个朝向，让 AEB 和规划重新判断，再按原方式重发；转向也失败才判受阻。

如果两侧都绕不出去，或者两次恢复机会用完，返回 `blocked`。

`blocked` 之后发生什么，是编排层的事：跳过这个点、播报「点位 X 无法到达」、继续下一个点；如果最后没回到起点，走降级收尾。**导航不替上层决定整轮巡检的生死**——这是接口分层带来的好处。

一个容易忽略的细节：判定受阻的瞬间就上报 `detour` 相位，此时车还停着。播报和绕行动作并行，而不是串行，现场观感差别很大。

## 七、安全边界：限速、AEB、软限位与走廊

### 7.1 限速：写入、回读、失败回滚、退出恢复

实机运动前读并备份底盘原有限速，再按巡检/返程配置写入（均为 `0.4 m/s`）。写完后**回读确认**，不一致就回滚原值并终止本段；节点退出时恢复备份。

限速不是「设一次就完事」的配置，它是一个会被别的进程改、会被固件重置的状态。不校验就等于没设。

### 7.2 AEB：每段开，`finally` 关

每段运动前开 AEB，轮询底盘动作到终态。失败、超时、取消都走同一条清理路径：

```text
取消底盘动作（cancel 约 50ms 内生效）
  → 停车
  → 关 AEB
```

顺序不能反。先关 AEB 再取消，中间那一小段车是「没人管」的。

### 7.3 软限位与走廊校验

两层保护，粒度不同。

**软限位**（`x: [-10, 45]`，`y: [-20, 20]`）只拦数量级错误——比如坐标单位写成了毫米、yaml 里多打一个零。它的作用是防止机器人收到一个「飞到楼外」的目标，不负责精细安全。

**走廊校验**才是真边界。巡检走廊在 y 方向的范围是 `[0.35, 3.450]`，再留 0.90m 安全边距，实际允许的横向范围是 `[1.25, 2.55]`。

这个数字是现场标出来的，过程有点丢人：

- 11 月 2 日实测，走廊左右两侧的中心分别是 `y = 2.550` 和 `y = 0.784`，按这个配了绕行范围；
- 11 月 3 日返程绕行，落点 `y ≈ 1.00`，车撞上了门框。

结论是：「中心线」不等于「安全线」。门框、灭火器箱、消防栓这些凸出物不在走廊中心线上，但它们才是真正的边界。所以下限从 0.784 收到 1.25（= 0.35 + 0.90），宁可少一点绕行空间，也不能再撞一次。

校验失败时的处理也有顺序：先尝试镜像到走廊另一侧，两侧都不可行就原地停车并播报，不硬走。

## 八、故障分级：为什么 WiFi 断了不该拦车

运动前会检查底盘健康状态，但「有故障」和「不能动」是两回事。

底盘用 DTC（诊断故障码）上报，导航侧按严重级分三类：

| 类别 | 例子 | 处理 |
| --- | --- | --- |
| A 类（FATAL） | 急停、驱动这类必须先处理的故障 | 拒绝运动，输出 DTC |
| B 类（ERROR） | 会让本轮任务不可靠的故障 | 拒绝运动，输出 DTC |
| C 类（WARNING） | 如 WiFi 未连接 | 只 WARN，不拦车 |

这里有个坑：底盘返回的健康对象里有一个聚合标志 `hasFatal`，**WiFi 未连接也会把它置真**。如果直接看这个标志，机器人会因为「没连上 WiFi」拒绝执行巡检——而巡检任务本来就不依赖 WiFi。

解决办法是按 DTC 分类自己过滤，而不是信聚合标志。这类「看起来是布尔值、其实是混合语义」的字段，在设备对接里非常常见。

定位检查也分模式：实机模式下 `slam_status != 0` 拒绝所有目标；`dry_run` 只告警。需要时可以触发重定位，超时 60 秒、每 0.5 秒轮询一次，初始位姿默认取起点。

还有一点：前置检查失败**不锁死**。后台每 5 秒重试一次，定位恢复了就自动放行，不需要人工重启节点。

## 九、测试：三层，各自解决不同的问题

### 9.1 dry_run：先验证逻辑

```bash
ros2 launch fire_inspection_nav navigate_to.launch.py
ros2 action send_goal /fire_inspection/navigate_to \
  fire_inspection_interfaces/action/NavigateTo "{poi: 'POI_01'}" --feedback
```

模拟模式不下发真实运动，用来检查：点位顺序、非法目标拒绝、返程条件、Feedback/Result 字段、取消与超时。

这一层跑得快，改完接口先在这里过一遍，能挡掉大部分低级错误。

### 9.2 单元测试：把「难复现」的场景固化

受阻恢复是最难现场复现的部分——你没法请一个人正好站在轨道中间，还配合你测三次。

所以这部分逻辑用测试固化，`tests/test_nav_stall_recovery.py` 有 684 行，覆盖：

- 停滞 → 后退 → 绕行 → 重发成功；
- 两侧绕行都失败 → `blocked`；
- 后退失败 → 原地转向脱困；
- 绕行落点受软限位约束（越界的一侧不选）；
- 返程绕行后按轨道重发，而不是回上轨点；
- `blocked` 之后顺序推进、编排层跳过该点。

另外还有健康分级测试（DTC 严重级、维护模式、WiFi 告警不拦车）和介入流程测试。这些用例跑起来是毫秒级，比实机试错便宜太多。

### 9.3 实机：低速、有人、急停在手

```bash
/home/nvidia/fire-inspection/run_nav.sh            # 实机
/home/nvidia/fire-inspection/run_nav.sh --dry-run  # 只检查不运动
```

首次实机保持低速、空载、有人现场守护。重点看：是否沿轨道走、是否准确到点、朝向对不对、停留时长、返程是否走专用轨道、异常时能否及时停。

介入场景（吸烟行为）还有限流：每个点位最多 1 次、全局最多 5 次、有冷却期、每段硬上限 3 次。没有限流的话，一个误检就能让机器人在原地反复横跳。

## 十、经验与后续

几条我认为值得记下来的：

**第一，接口要把「失败」拆细。** `failed` / `blocked` / `cancelled` / `timeout` 的处置方式完全不同，混成一个布尔值，上层就只能一刀切。

**第二，别信设备返回的「进度」字段。** 剩余距离、剩余时间这类字段，在异常路径上经常是错的。用自己的观测（位姿、位移）做判断，慢一点但准。

**第三，能自恢复的故障和不能自恢复的故障要分开。** 卡住可以后退绕行，但「绕两次还不行」就该上报，而不是无限重试。

**第四，参数要能现场改。** 走廊边界、绕行距离、停留时长全在 yaml 里，改完重启节点即可，不用重新编译。现场标定是常态，不是例外。

**第五，测试要覆盖「最难复现的那部分」。** 顺畅路径谁都能测，真正值钱的是受阻、打断、越界这些场景。

后续还想推进的：

- 走廊参数按多个现场标定，做成可切换的配置档，而不是一套全局值；
- 多障碍物场景下的绕行策略（现在只处理单点受阻）；
- 网络抖动时的动作状态恢复（轮询失败目前只是继续轮询，断连久了会怎样还没系统测过）；
- 把现场调试记录整理成「现象 → 判断 → 处理」的排查表。

## 十一、总结

天轶 2.5 的导航模块，核心不是「让机器人走到点位」，而是**让这段运动可解释、可中断、可恢复**。

轨道和点位解决了「按顺序走对路」，Action 接口解决了「上层能看见过程」，受阻自恢复解决了「卡住了怎么办」，分段返程解决了「被打断之后怎么接着走」。这些东西单独看都不复杂，但组合起来才是现场能用的导航。

如果只让我留一句话：**导航模块的价值，一半在正常路径上，另一半在异常路径上。** 而后者，往往要等到真正跑起来才会暴露。
