上一篇我们聊了 SLAM——机器人怎么在陌生环境里边走边画，攒出一张 5 厘米一格的地图。文末留了个钩子：路径规划，规划的就是在这张图上，从起点到终点找一条只走白色像素的线。

很多人第一次把 Nav2 跑起来，遇到的往往不是「找不到路」，而是另一堆怪事：从两个货架中间穿过去，车身蹭了一侧；明明有直路，它偏要绕个大弯；走着走着突然原地转圈，转完又像没事一样。

回头翻文档找原因，扑面而来的是 Planner Server、Controller Server、Costmap、DWA、A*、重规划……一层压一层，不知道从哪下手。

其实把这些名词放一边，路径规划的本质用一句话就能说清：

> **机器人走的从来不是「一条路」，而是两层各管一段：全局规划负责「选哪条路」，局部控制负责「沿着这条路走的时候，别撞上计划外的东西」。**

这篇文章就沿着这两层往下拆，最后在 Nav2 里亲眼看一看它们各自长什么样。

适用环境：ROS 2 Humble + Nav2（Ubuntu 22.04 / Docker 中的 Humble 均适用）

---

## 一、先看一个生活场景：开车用导航

你开车出门前，高德地图会给你一条推荐路线：走快速路，避开拥堵，预计 32 分钟。上路之后呢？你其实一刻也没「照着」这条线开——前面修路你借道绕一下，旁边电动车贴上来你收一脚油，有人加塞你让一把。只有当前方彻底堵死，你才会点一下「重新规划」。

整个过程拆开看，跟机器人导航严丝合缝：

| 导航 App / 你的动作 | 机器人导航系统里的模块 |
| --- | --- |
| 出发前选一条整体路线 | **全局规划（Planner）**——起点到终点选一条路 |
| 途中躲人、躲车、微调方向 | **局部控制（Controller）**——沿路走，实时避障 |
| 前方堵死，点「重新规划」 | **重规划**——路径失效时重算 |
| 下载的离线地图 | **代价地图（Costmap）**——路网的路况底账 |

注意一个细节：你从来不会因为「躲了个电动车」就整趟重新规划路线——那是小事，局部处理掉就行；但「前方高架封了」就必须重算。**什么时候该局部兜一下、什么时候该整趟重算，是这套系统最见功夫的地方。**

## 二、为什么一层不够，非要分两层

初学者最容易冒出的念头是：直接从起点到终点算一条路，机器人照着走不就完了？

不行。两层各砍掉一层，两头都会翻车：

- 只做**全局**规划：规划那一刻障碍物是真的，可走廊里随时有人推着车经过——一条静态路线碰上动态世界，必撞；
- 只做**局部**避障：机器人哪边空往哪边钻，钻进死胡同出不来，或者绕来绕去离目标越来越远。

所以工程上的答案是拆开，各自用自己擅长的方式干活：

| | 全局规划 | 局部控制 |
| --- | --- | --- |
| 视野范围 | 整张地图 | 机器人周围几米 |
| 管多远的事 | 全程路线 | 未来几秒 |
| 算的频率 | 低频（1 Hz 上下） | 高频（10~20 Hz） |
| 用什么信息 | 静态地图 + 已知障碍 | 实时传感器数据 |
| 典型算法 | Dijkstra（NavFn）、A*（SMAC） | DWA / DWB、TEB |

一句话记住分工：**全局规划慢思考、看大局；局部控制快反应、看眼前。** 两层的运行频率差着一个数量级，这是理解后面所有内容的钥匙。

## 三、全局规划：在白色像素里找最短路

接上篇的设定：占据栅格地图上，白色像素可走、黑色是障碍。所谓全局规划，就是把这张图变成一张「网」，再在网上找一条最短路。

### 把地图变成网

把每个白色像素看成一个节点，跟它上下左右（或八个方向）相邻的白色像素连一条边，整张地图就变成了一张巨大的图。剩下的就是图搜索：从起点那个格子出发，一步步往外扩，扩到终点，路就出来了。

### Dijkstra：一圈一圈往外扩

最经典的搜法是 Dijkstra：从起点出发，按「离起点由近到远」的顺序一圈一圈扩展，像水波扩散，碰到终点就停。它保证找到的是最短路，毛病却很明显——**不分方向，四面均匀扩散**。终点明明在东边，西边、南边照样一寸寸探过去，地图一铺开，大半算力花在明显不通的方向上。

### A*：带着「直觉」搜索

A* 在 Dijkstra 上加了一样东西——启发函数（heuristic）。每扩展一个节点，它算两个值：

- g：从起点走到这个格子，已经花了多少；
- h：估一下这个格子离终点还有多远（通常直接量直线距离）。

然后优先扩展 g + h 最小的节点。直白地说：

> **Dijkstra 是水波均匀扩散；A* 是水波带着「往终点去」的倾向扩散——终点在东，东边的波纹就跑得快，西边的几乎不动。**

| | Dijkstra | A* |
| --- | --- | --- |
| 扩展顺序 | 离起点由近到远 | 离「起点 + 估算终点」综合最近 |
| 速度 | 慢，盲探 | 快，带方向感 |
| 结果 | 严格最短路 | 一样最短路（h 不高估时） |
| 适合场景 | 目标不明 / 多目标 | 点对点导航（绝大多数场景） |

这里有一处常见误会要澄清：**Nav2 默认的全局规划器 NavFn 其实是 Dijkstra**，稳当但不算快；想要 A* 的方向感，得把插件换成 SMAC Planner 的 2D 版本。点对点导航，方向感就是效率。

## 四、代价地图：从「能不能走」到「走这里多亏」

这里有个容易被忽略的地方：栅格地图只有黑白灰，黑是禁行、白是可行。照这个规则，贴着墙走和走通道正中**一样好**——反正都是白格子。

但现实里贴墙走是会剐蹭的。这就是代价地图（Costmap）出场的地方：它把每个格子从「能不能走」升级成「走这里代价多大」：

- 障碍物本身：无穷大，禁行；
- 障碍物往外一圈：离得越近代价越高，**膨胀层（inflation）**干的事；
- 正常通道：代价低。

规划器搜索时不再只算「路有多长」，而是算「一路走下来总代价多少」，机器人自然挑离障碍物有余量的路线走。

我们项目里真实翻过这个车：天轶机器人在一段窄走廊里，右侧车体总蹭墙，我一开始怀疑是控制参数的问题，查了一圈，最后发现是 `inflation_radius` 设小了——墙的「代价圈」没罩住车体宽度，规划出来的路贴墙太近。把半径从 0.15 调到 0.35，当天就没再蹭过。

**机器人莫名剐蹭、贴墙、绕不开东西，先查 inflation，再怀疑别的。**

另外，代价地图在 Nav2 里其实是两份：

- **全局 costmap**：以静态地图为底，覆盖整张地图，给规划器用；
- **局部 costmap**：只看激光雷达当前几米内的实时数据，滚动更新，给控制器用——这正好对上第二节的「两层分工」。

## 五、局部控制：DWA 是怎么边走边躲的

全局路径只是一条几何线：没有速度、没有时间、不知道下一秒有人挡路。把它变成「每 0.1 秒一组速度指令」的，是局部控制器。Nav2 默认挂的是 DWB——DWA（动态窗口法）的工程化改进版，思路一脉相承。

它的思路朴素得近乎粗暴，就三步：

1. **采样**：机器人在一个瞬间能选的速度是有限的——受电机加速度限制，此刻速度 v、角速度 ω 只能在一个小窗口里挑。在这个窗口里均匀抓一把候选（常见二十来组）；
2. **模拟**：每组速度往前推演一两秒，各自画出一条小轨迹——这么走下去会到哪、会不会蹭上；
3. **打分**：给每条小轨迹打分，谁分高执行谁。分数看三样——离障碍物多远（快撞的不行）、离全局路径偏了多少（别跑偏）、走得快不快（别磨蹭）。

执行胜出的那组速度，走一小步，然后推倒重来——每秒 20 次。

类比开车：没人会预先算好未来 500 米每一把方向的角度，都是瞄一眼前方、定个大致方向、每零点几秒修一次。DWA 做的就是把这套直觉数字化。

另一个常被提到的控制器是 TEB：它把「未来几秒的整条轨迹」当一根橡皮筋，一头往目标拉、一边躲着障碍物做优化，比 DWA 看得更远，代价是算得更重。新手用 DWB 入门足够，真撞上天花板再换。

## 六、走偏了怎么办：重规划不是失败

局部控制器能躲小障碍，但两种情况它兜不住：

- 障碍把整条路堵死（局部轨迹打分全不及格，机器人原地打转）；
- 机器人被卡住超过一定时间。

这时候就触发**重规划**：拿着全局 costmap 把整条路重算一遍，绕开堵死的那段。上一篇天轶那篇文章里写过的「受阻自恢复」，底层就是这套机制：先尝试原路，超时后触发重规划换路，实在不行再执行恢复动作（原地旋转重观察、后退脱困）。

所以再次强调一个观念：

> **重规划不是系统出了故障，而是它的日常呼吸。一个从不重规划的机器人，反而说明环境太假了。**

## 七、在 Nav2 里亲眼看这两条线

概念拆完了，跑起来看实物。Nav2 起来之后，这几条话题（topic）就是两层的「现场直播」：

| 话题 | 内容 | 对应层 |
| --- | --- | --- |
| `/plan` | 全局规划器算出的整条路线 | 全局 |
| `/local_plan` | 控制器当前几秒的轨迹 | 局部 |
| `/global_costmap/costmap` | 全局代价地图 | 全局 |
| `/local_costmap/costmap` | 局部代价地图（滚动窗口） | 局部 |

RViz 里把这几条依次添加，牵着机器人走一段：`/plan` 是一条贯穿地图的粗线，稳稳不动；`/local_plan` 是贴着机器人的一小截曲线，不停抖动重画。**一静一动，两层分工肉眼可见——这一眼比翻十页文档管用。**

调参时最常用的几个旋钮，按踩坑频率排序：

| 参数 | 作用 | 调大的效果 |
| --- | --- | --- |
| `inflation_radius` | 障碍物的代价圈半径 | 离墙更远、更安全，窄通道可能过不去 |
| `controller_frequency` | 控制器频率 | 反应更快，CPU 占用升高 |
| `yaw_goal_tolerance` | 到点朝向容忍度 | 调小会到点反复对角度 |
| `xy_goal_tolerance` | 到点位置容忍度 | 调小会到点来回蹭 |

窄通道过不去和贴墙剐蹭，本质是 `inflation_radius` 一根扁担挑两头：太小剐蹭、太大过不了窄门。工程上的定法很朴素——**代价圈半径 ≈ 机器人半径 + 一拳富余（15~20 厘米），再按现场实测修。**

## 八、常见误区

**误区一：剐蹭是控制器的锅。**
多数时候是 inflation 半径不够，路本身选得太贴墙——规划问题，不是执行问题。

**误区二：costmap 分辨率越高越好。**
格子从 5 厘米缩到 2 厘米，格子数翻六倍多，规划耗时平方级上涨。0.05 米是室内场景的甜点值，没有硬理由别动。

**误区三：局部避障是万能的。**
速度太快刹不住（DWA 只往前推演一两秒）、桌腿货架腿这类细障碍在激光里只落下一两个点、玻璃墙干脆看不见——这是物理上的事，算法兜不住底。该降速降速，该人工标禁行区就标。

**误区四：导航一失败就查规划器。**
我们排障时的真实分布大致是：一半是定位漂了（AMCL 和现实对不上，机器人「以为」自己在别处）、三成是地图旧了（格局早改了）、剩下一成多才是规划参数。**先拿 RViz 看机器人位姿和现实对不对，再谈规划。**

**误区五：路径抖 = 参数烂。**
`/local_plan` 本来就该抖——每秒重算 20 次的小轨迹，抖是工作状态。该担心的是 `/plan` 频繁整体变脸，那通常意味着定位不稳。

## 九、一句话总结

- 路径规划分两层：**全局选路，局部避障**——一层慢思考看大局，一层快反应看眼前；
- 全局规划就是**图上搜索**：Dijkstra 四面均匀扩散（NavFn 就是它），A* 带「往终点去」的方向感（SMAC 用它）——要稳选前者，要快选后者；
- 代价地图把「能不能走」升级成「**走这里多亏**」，inflation 层专治贴墙剐蹭；
- DWA 的循环就三步：**采样速度、模拟小轨迹、打分执行**，每秒重复 20 次；
- **重规划是日常呼吸，不是故障**——不重规划才可疑；
- 导航失败先查**定位和地图的新鲜度**，最后才轮到规划参数。

学路径规划不用先啃图论，但要能回答三个问题：全局和局部为什么必须分两层？inflation 到底在防什么？DWA 每个周期在干什么？这三个想通了，看 Nav2 的参数文件就不再是天书。
